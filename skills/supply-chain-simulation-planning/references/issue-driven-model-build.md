# Issue 驱动的仿真建模流程

本规范把项目计划拆成有依赖、有验收证据的 Issue 工作包。参考了 Aerospace `issues/01.md` 至 `14.md` 的迭代方式：先统一口径和数据，再验证脆弱机制，搭建公共骨架和最小流程，逐次增加模型复杂度并在每次增加后验证，按用户需要定义基线，最后逐项比较方案并交接。Issue 数量不固定；工作责任和阶段顺序必须清楚。

项目使用 GitHub 协作时，本文件继续定义 Issue 的工作内容和验收结构；GitHub 状态、Pull Request、受控文件变更、模型版本与运行证据之间的治理关系按[GitHub 仿真项目治理](github-project-governance.md)执行。不要为了接入 GitHub 重复维护两份互相漂移的 Issue 正文或状态。

## 设计规则

- 项目路线文件 `01.md` 是总索引，必须确定迭代轮次、依赖关系、阶段门和交付物，并把路线映射到具体 Markdown Issue。
- 核心工作包编号 `01–14` 和迭代轮次是不同维度。每个启用的核心工作包 Issue 对应单独的 Markdown 文件，例如 `iterations/I1/04.md`；文件名中的 `04` 表示工作包，目录中的 `I1` 表示迭代轮次。
- 模型演进使用两层路线标记：`I1`、`I2`、`I3`……代表不断丰富模型的迭代轮次；`.1` 至 `.7` 代表每轮默认环节。因此 `I1.1–I1.7` 是第一轮路线中的七个环节，`I2.1–I2.7` 是第二轮同类环节。它们是 `01.md` 总路线表中的阶段标签，不替代核心工作包的 Markdown 文件编号。迭代轮数不设上限。
- 每轮应按默认次序检查 `.1` 本轮目标（工作包 01）、`.2` 数据与机制定义（02、03）、`.3` 脆弱机制原型（04）、`.4` 模型增量（05、06）、`.5` 新增机制验证（07、08）、`.6` 回归与状态确认（09 如适用）、`.7` 本轮评审与交接（10–14 中适用的工作包）。平台专属的 Simio 实现方式由 `simio-modeling` Skill 负责；本规划 Skill 只登记业务机制、输入、验收和证据边界。可将多个责任合并到单个 Issue 文件，也可拆出子 Issue；`01.md` 总路线必须记录每个环节与实际文件的映射。
- 每个模型构建 Issue 必须登记继承版本、本次新增复杂度、产生的新版本、验证新增机制的方法和既有验证的回归结果。下一轮须明确继承哪个已验收版本；若从旧版本分支，说明原因和差异。
- 保持核心编号语义稳定，便于不同项目复用和审阅。项目可合并低风险工作包、拆分高风险工作包、增加专项 Issue；记录调整理由，保留被合并工作包的验收责任。
- 状态用 `Required`、`Optional`、`N/A`。关键机制未验证、运行模型未做确定性验证、或项目范围要求某交付时，该工作包不得标为 `N/A`；记录不适用的依据。
- 编号提供默认顺序，依赖图才是实际执行约束。可并行的独立任务可并行，所有前置验收未完成的工作不得进入依赖阶段。
- Issue 状态至少区分 `Planned`、`In Progress`、`Blocked`、`Passed`、`Rework`、`N/A`。`Passed` 必须有模型/数据版本、实际结果和证据位置。
- 预测值、解析值和实际仿真结果分别标注。每个 Issue 记录预期与实测偏差、解释、返工和对下游设计的影响。

## 默认核心工作包

| Issue | 默认工作包 | 核心输出与验收重点 | 默认依赖 | 使用条件 |
|---|---|---|---|---|
| 01 | 项目目标与路线 | 决策问题、边界、阶段分解、Issue 清单与依赖图、成功标准、责任人和总体阶段门 | 无 | 始终 Required |
| 02 | 建模口径与假设 | 术语、单位、时间和统计口径；事实/假设/实现选择/未知；版本化假设登记 | 01 | 始终 Required |
| 03 | 数据架构与输入快照 | 数据字典、主外键、输入快照、来源谱系、质量与单位检查、转换规则 | 02 | 需要数据驱动模型时 Required；解析项目也须登记数据来源 |
| 04 | 最小机制原型 | 对高返工风险机制做小模型试验，给出通过判据、备选设计和原始证据 | 02、03 | 机制脆弱或平台语义未知时 Required，否则可说明 N/A 理由 |
| 05 | 公共模型骨架 | 实体、资源、日历、状态、基础路由、命名和共享数据责任 | 02、03；如适用则 04 | 原生模型建造时 Required |
| 06 | 初始流程模型 | 可运行的最小完整流程；明确投放、处理、队列、转移、结束及排除项 | 05 | 原生流程模型时 Required |
| 07 | 指标与统计框架 | 指标总体、分子/分母、边界、单位、终止和删失处理；响应实现和解析口径 | 01、02；模型响应可依赖 06 | 需要仿真输出或方案比较时 Required |
| 08 | 确定性验证与守恒 | 单体/小批量、时序、资源、日历、边界、守恒和回归测试；预期推导、容差、实际证据 | 06、07 | 运行模型前 Required；不适用随机性的测试仍应执行 |
| 09 | 用户定义基线/研究状态 | 用户指定参考状态的冻结模型/数据版本、建立理由、运行证据和可信度边界 | 02、03、06、07、08；或用户指定的前一迭代 | 仅当用户要求基线、或决策比较需要参考状态时 Required；基线可以是当前、校准、目标或其他状态 |
| 10 | 流程/控制策略实验 | 研究直接改变流程行为的方案，如批量、缓冲、投放、派工和路由；锁定共同控制并定义实验设计 | 08；如有现状基线则依赖 09 | 按决策需要启用，可拆成多个 Issue |
| 11 | 资源与人员实验 | 研究技能、共享资源、灵活用工、人员分配和资源池 | 08；涉及基线比较时依赖 09/10 | 仅当人员/资源策略属于决策问题时启用 |
| 12 | 产能与结构实验 | 研究产品组合、并行设备、第二条线、布局或工艺平衡 | 08；常依赖 10/11 的候选方案 | 按模型结构和产能决策裁剪 |
| 13 | 日历与运营策略实验 | 研究班次、加班、维修、换型、释放和库存策略 | 08；实验交互由 01 的依赖图规定 | 按决策需要启用，可拆成多个专题 |
| 14 | 报告与交接 | 建议、比较结果、不确定性、成本和落地限制；模型/数据/运行身份、复现步骤和局限 | 已计划的基线和实验 | 正式交付时 Required；如项目裁剪编号，仍保留交接责任 |

默认核心工作包 `01–14` 提供跨项目稳定的责任分类；每轮各自建立 Issue 文件，例如 `iterations/I1/06.md`、`iterations/I2/06.md`。两份文件都对应工作包 06，但分别记录不同迭代的模型增量。项目级 `01.md` 是总路线索引，需说明 `I1.1–I1.7`、`I2.1–I2.7` 等阶段标签如何映射到各轮的 Issue 文件。实验较多可增加工作包子编号，轮次和依赖仍须清楚。

## 建议依赖图

```text
项目路线 `01.md`
  → I1.1 → I1.2 → [I1.3] → I1.4 → I1.5 → I1.6 → I1.7
       ↳ iterations/I1/01.md ... iterations/I1/14.md（按需启用）
  → I2.1 → I2.2 → [I2.3] → I2.4 → I2.5 → I2.6 → I2.7
       ↳ iterations/I2/01.md ... iterations/I2/14.md（按需启用）
  → I3.1 ... （直到用户要求的模型状态和交付条件满足）
```

方括号内的机制原型按风险启用。每轮的 `.1–.7` 是默认检查环节；确实不适用的环节可标明 `N/A`，模型增量、验证、回归和轮次评审责任不可因裁剪而丢失。09 不是所有项目都需要的“当前状态基线”；若定义基线，必须在 `01.md` 和项目基线模板中标明所属轮次、Issue、版本及用途。项目不建立基线时，照常按迭代路线推进到用户要求的研究或交付状态。

## 复杂度裁剪

- **简单分析或小模型：** 可把 02+03、05+06、06+07 合并成较少 Issue；保留独立章节/验收项，避免范围和指标被埋在实现描述里。
- **高机制风险：** 将 04 拆为多个 Spike，例如批处理、共享技能资源、换班暂停、故障恢复、动态路由；每个 Spike 只验证一个关键不确定点。
- **数据复杂或多源：** 拆分 03 的来源盘点、转换、质量、快照和绑定验收，并固定一个可重现的数据版本。
- **多策略、多决策：** 每个独立决策问题或强交互因素组建立实验 Issue，避免在一个大 Issue 中混合多个机制和不同统计总体。
- **仅做模型核查：** 可以不创建 05/06 等建模实施包；建立核查范围、证据获取、独立复算、跨版本比较、发现和关闭工作包。

## 每个 Issue 的最小模板

```markdown
## 目标与决策问题
## 迭代编号（轮次.环节）与核心工作包映射
## 核心工作包编号与本轮文件名
## 依赖与进入条件
## 迭代定位与继承版本
## 固定控制和输入版本
## 本 Issue 允许的模型/数据变更
## 新增复杂度与预期行为
## 实施步骤与责任人
## 预期结果及独立推导
## 验证用例、容差和失败处理
## 既有验证的回归结果
## 实际结果、偏差解释与证据路径
## 基线标记（None / Baseline / Scenario）及理由
## 产生的模型、数据和结果版本
## 阶段门和下游影响
## 状态与版本身份
```

启用 GitHub 管理时，在 Issue 文件的状态段或交接段追加：

```markdown
## GitHub 闭环记录
- GitHub Issue：#<number>
- Local status：Passed
- Decision owner：
- Business reviewer：
- Approval reference：
- Evidence commit：
- Evidence paths：
- GitHub sync：Pending / Audited / Closed
- Sync receipt：通道、实际动作、回读时间与证据位置
```

本地 `Passed` 只表示本 Issue 的验收范围完成；线上 `closed` 必须在证据提交、业务评审、验收评论和状态标签完成后登记。详细规则见[GitHub 仿真项目治理](github-project-governance.md)。

用 Issue 验收记录实际结果。若验收失败，记录失败证据、影响的架构决策、返工版本和需要重跑的回归测试；不得仅把 Issue 状态改成完成。

## Aerospace 来源的抽象边界

Aerospace 的编号结构展示了可迁移的迭代逻辑：假设 → 统一数据表 → 最小机制 Spike → 公共骨架 → 初始流程 → 指标 → 确定性验证 → 现状基准 → 分专题实验 → 报告交接。其飞机型号、四日脉动、traveled work、机械师配置、具体实验主题和数值属于该案例，不是通用 Issue 默认值。
