# GitHub 仿真项目治理

本参考适用于把仿真项目放在 GitHub 协作管理的场景，包括模型主要在本机仿真软件中开发、之后把模型快照和证据提交到仓库的项目。它补充 Issue 驱动建模流程，不取代业务建模、仿真验证或 Issue 验收要求。治理强度应与团队规模、决策风险和交付责任相称。

## 记录职责与权威来源

为每类信息指定一个权威来源，避免在 GitHub Issue、路线文档、看板和状态汇总中重复维护不同版本的事实。

| 记录 | 主要职责 | 修改方式 |
|---|---|---|
| 项目章程（可选） | 项目授权、决策责任人、目标、范围边界、成功标准及重要约束 | 经批准后纳入版本控制；范围或授权变化通过 Issue 和 PR 修订并记录影响与批准信息 |
| 项目路线 `01.md` | 迭代轮次、阶段映射、依赖、阶段门和交付路径 | 随项目演进，可经关联 Issue 和 PR 调整；它是活动路线索引，不自动等同于项目章程 |
| 假设与模型契约 | 术语、输入含义、模型边界、业务规则、状态、指标和实现约束 | 受控的设计记录；变更关联 Issue，说明受影响的实现、结论和回归验证 |
| GitHub Issue | 工作目标、依赖、设计/变更范围、验收条件、预期结果、责任状态及关闭依据 | 作为工作项状态和验收的权威入口；需要长篇规格时，Issue 链接仓库中的受控文件，不复制并分别维护两份正文 |
| Pull Request | 展示一组可审阅的仓库变更，关联 Issue 并呈现验证证据 | 通过 PR 合入；说明变更、版本身份、检查结果、限制和未完成项 |
| 运行/验证记录 | 记录一次具体测试或实验的配置、原始结果、判定和证据位置 | 已用于验收的记录不得被新结果静默覆盖；纠错或复跑应新增记录并指出被更正或替代的 Run ID |
| 模型/输入清单与发布清单 | 将模型文件、数据、实验结果、提交和正式交付包绑定 | 随快照或发布更新；记录精确文件身份、哈希、范围和验证状态 |
| Milestone、Project 看板与 Labels | 汇总阶段、工作流状态和工作类别 | 用于导航和进度视图；不取代 Issue 验收、模型证据或正式版本记录 |

项目章程不是强制文档。若项目需要正式授权或跨团队审批，章程应说明谁有权批准目标、范围和重大变更；否则可在项目路线中明确这些责任。章程描述“项目获准做什么以及如何判断成功”，不承载当前模型状态、Issue 进度或逐次运行结果。

`project-baseline.md` 模板是项目规划、迭代路线和状态登记模板。基线是可选的用户定义参考状态；项目路线、模型契约和正式交付都不应因此被误认为必须建立基线。

## 受控修改

- 已批准的章程、范围、成功标准或关键假设可以修订，但必须有可追溯的变更请求、原因、影响分析和批准记录。Git 提交及 PR 历史用于保留版本；只有当下游记录需要引用明确的批准版本时，再维护独立的文档版本号，避免重复维护变更台账。
- 路线和模型契约允许随新信息迭代。每次会改变工作顺序、模型行为、数据语义或结论解释的修改，都要关联 Issue，并说明影响哪些阶段、模型版本、验证和既有结论。
- 新发现的差异应通过新 Issue 或重新打开相关 Issue进入正式流程。保留原结果及其适用版本，记录影响分析和需要重跑的验证；不能通过改写旧报告把新解释伪装成原始结论。
- 一个工作项可以有多个紧密相关 PR；每个 PR 都应指明关联 Issue 和其自身引入的证据。合并 PR 不自动代表 Issue 验收通过。
- 共享团队可要求具备领域能力的审查者确认模型语义和证据。单人维护时，不要把自我合并或单人 CODEOWNERS 描述成独立审查；记录实际审查边界，并用仓库检查和可复核证据补强。

## Issue、PR 与本地仿真工作

开始修改前，从已批准的项目路线和 Issue 确认本次允许的模型/数据增量、依赖、固定条件、预期结果、验收判据和回归范围。项目路线中的迭代标识（例如 `I2.3`）与 GitHub Issue 编号是不同标识，Issue 正文或路线索引应明确两者映射。

本机仿真软件中的修改也要进入仓库审查链：在主题分支开展工作，保存受控模型快照和必要输入/结果，记录文件哈希及原生验证证据，再通过 PR 汇总差异。若工具无法保存、导出或独立确认某项信息，明确标注缺口和责任人，不用口头确认替代仓库证据。

PR 至少说明：

- 关联 Issue，以及本次改变的模型机制、数据或文档；
- 修改前后模型和输入身份，涉及的实验/场景及结果路径；
- 静态检查、原生诊断、运行/Experiment、保存重载检查中实际完成的项目；
- 验证结果、限制、未完成事项，以及对既有结果或下游 Issue 的影响。

检查强度按项目适配。自动检查可以验证文件存在、格式、哈希、映射、结果列或其他可机器判断的不变量；它不能证明 Simio 内部逻辑正确、模型结果有效或运营行为已确认。Issue 只有在自身验收条件满足，或未满足项已按责任人批准的方式明确处置时才关闭。Project 看板进入“完成”列、PR 合并或模型文件已上传，都不能单独作为验收依据。

## 运行证据与版本绑定

每个被用于 GitHub 项目验收或方案结论的 Run/Experiment 都必须关联至少一个 GitHub Issue；探索性运行在被用于结论前也要补上 Issue 关联，并标明其探索性质。记录还应能追溯到：

- 关联的 Issue，以及产生该模型/运行变更的 PR 和 Git 提交（如适用）；
- 精确模型文件及 SHA-256，或不可变的模型版本/提交；
- 输入数据快照及转换版本；
- 仿真软件版本、Experiment、Scenario、控制参数、随机流和重复设置；
- 响应定义、原始结果路径、单位和时间边界；
- 预期与实测、容差、守恒/独立复核、通过判定和限制；
- 运行后模型是否保存、关闭/重载并重新核验（当交付声明依赖持久化时）。

项目可以使用一个 Run Manifest 或按 Issue 存放验证记录；字段应足以复现该结论，不要求固定文件名。禁止把不同模型/输入版本的同名 BASE 或场景结果拼接为一个总体，除非研究设计明确建立了可比性并记录依据。

最小追溯链为：`迭代环节 → GitHub Issue → PR/提交 → 模型与输入快照 → Run/验证记录 → 结果与结论 → Release（如已发布）`。项目可以合并或拆分其中的文件，但不能丢失这些关系。

## 版本、检查点与发布

区分三个身份：Git 提交标识仓库内容；模型版本或模型文件哈希标识仿真包；Release 标签标识批准发布的交付集合。三者可以关联，但名称相似不证明它们内容一致。

- 在有意义的迭代验收点保存模型快照。大型二进制模型可用 Git LFS 或受控制品存储，并在仓库记录哈希、大小、来源、兼容软件版本和相关证据。
- 候选快照和阶段性标签可用于恢复/比较；只有完成所需验收和交付核验后，才标为正式 Release。标签、Issue 关闭或文件名中的 `Final` 都不能替代冻结检查。
- Release Manifest 应列出 Git 提交、模型文件和哈希、输入/结果制品、验证记录、适用范围、已知限制及复现说明。涉及保存状态的交付，应对最终文件执行保存后关闭/重载和关键回归核验。
- 若后续发现可能改变推荐的重要模型差异，建立跟进 Issue，评估受影响的历史实验和 Release；旧版证据仍保留，修订结论通过新 PR 发布。

GitHub Milestones 可按阶段或决策包组织 Issue；Project 看板表示工作状态；Labels 表示工作类别或证据状态。保持它们同步且含义清楚，但不要把任一视图当成验收证据。所有开放 Issue 和未合并分支均应有明确状态；未进入 `main` 或正式 Release 的结果不得作为当前批准项目结论引用。
